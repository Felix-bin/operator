# FlashAttention V1 图解

<p class="gpu-lede">同一次 GPT-2 Attention 的前向加反向，FlashAttention 比标准实现多做约 13% 的浮点运算，从 66.6 GFLOPs 涨到 75.2 GFLOPs，耗时却从 41.7 ms 降到 7.3 ms，快了 5.7 倍。多出来的计算没有拖慢它，因为真正变化的是另一个数：HBM 读写量从 40.3 GB 降到 4.4 GB。</p>

这组数字来自[论文](https://arxiv.org/abs/2205.14135)的 Figure 2，条件是 A100、序列长度 1024、头维度 64、16 个 head、batch 64。本文讲这 36 GB 是怎么省下来的，并回答三个问题：块该切多大，为什么结果还是精确的，反向传播要的矩阵去哪了。

阅读前最好先看过[Roofline](../about_gpu/ai-compute#roofline)和[Grid、Block、Warp、Thread 的对应关系](../about_gpu/gpu#grid)。矩阵乘本身的优化见[GEMM 图解](../gemm/gemm)，Online Softmax 的详细推导见[Online Softmax 图解](../softmax/online-softmax)，这里只讲它在分块上的用法。

## 标准 Attention 把时间花在哪 {#bottleneck}

Scaled Dot-Product Attention 只有三个式子，其中 $Q, K, V \in \mathbb{R}^{N \times d}$，$N$ 是序列长度，$d$ 是头维度：

$$
S = QK^\top / \sqrt{d}, \qquad P = \text{softmax}(S), \qquad O = PV
$$

输入和输出都是 $N \times d$，中间的 $S$ 和 $P$ 却是 $N \times N$。$N = 4096$、$d = 128$ 时，$Q$ 用 FP16 存只要 1 MiB，$S$ 要 $4096 \times 4096 \times 2$ 字节，即 32 MiB，大了 32 倍。中间结果比输入输出都大，而且它们只是过渡，最终都不要。

标准实现的问题是把这些过渡结果真的写到了 HBM。三步是三个独立的操作，上一步的输出要写出去，下一步再读回来。

为什么不能直接把三步合成一个 Kernel？这正是常见的 kernel fusion，但在这里有两个障碍。第一，softmax 的分母要等一行的所有分数都算出来才知道，而一行分数放不进 SRAM。第二，反向传播还要用 $S$ 和 $P$。下面的技术就是分别解决这两点。

### 算术强度说明了什么 {#intensity}

两次矩阵乘共 $4N^2d$ 次浮点运算（每次 $2N^2d$，暂不计 softmax），读写 $4N^2 + 4Nd$ 个 FP16 元素，所以：

$$
\text{AI} = \frac{4N^2 d}{2(4N^2 + 4Nd)} = \frac{Nd}{2(N + d)} \approx \frac{d}{2} \ \text{FLOP/byte}
$$

约等号要求 $N \gg d$。严格说，这个比值的量级是 $\Theta(\min(N, d))$，实际场景里序列比头维度长，也就是 $O(d)$。下面把它放到 A100 的 Roofline 上看。

标准实现落在转折点左侧很远的地方，增加算力没有用，带宽先到头。FlashAttention 的读写量约为 $12N^2d^2/M$（[推导见后](#io)），代入后强度约为 $M/(6d)$，反而随 $d$ 变小而升高，并且把算子推到转折点附近。这也解释了开头的矛盾：多做 13% 的运算几乎不影响耗时，因为此时计算本来就不是瓶颈。

<p class="gpu-note">表中 N = 4096，全部按 FP16，只计矩阵乘的运算量，M = 98304。转折点取 312 TFLOP/s 除以 2039 GB/s。</p>

## 思路：中间结果不落地 {#idea}

论文把方法概括成两个已有技术的组合。分块（tiling）把矩阵切成小块，让一次计算的全部数据都能待在片上。重计算（recomputation）让反向传播不必保存 $S$ 和 $P$，用到时再算一遍。

分块之所以能成立，前提是 softmax 能拆开算，这就是 Online Softmax 在这里的作用。论文同时参考了 Milakov 和 Gimelshein 的 [Online normalizer calculation](https://arxiv.org/abs/1805.02867)。

## Softmax 怎么分块算 {#online}

一行分数 $x$ 被切成 $x^{(1)}, x^{(2)}$ 两段时，只要记住每段的最大值 $m$ 和以它为基准的指数和 $\ell$，整行的结果就能合成出来：

$$
m(x) = \max\big(m(x^{(1)}), m(x^{(2)})\big)
$$

$$
\ell(x) = e^{m(x^{(1)}) - m(x)} \ell(x^{(1)}) + e^{m(x^{(2)}) - m(x)} \ell(x^{(2)})
$$

对分块来说，一行的 $K$ 被切成 $T_c$ 段，这个合并就做 $T_c$ 次。下图用一行 6 个分数走一遍，每块 2 个。

  <figcaption>图中数值由组件现算。青色是这一块新算出的权重，琥珀色是之前的权重。之前的权重不会单独保存，它们已经折叠进 O，修正 O 就等于同时修正了它们。最后一行是一次性算出的 softmax，权重和 O 都与第 3 块后的结果相同。</figcaption>
</figure>

要注意的是 $O$ 这一列。论文 Appendix C 用的归纳假设正是这个：第 $j$ 轮结束后，$O$ 等于只看前 $j$ 块 K/V 时的正确 Attention 结果。每读一块，都把旧 $O$ 乘上 $\alpha \ell_{\text{old}} / \ell_{\text{new}}$，再加上新块的贡献。这里没有任何近似，所以结果只有浮点舍入带来的差异。

## 块怎么切 {#tiling}

### 块大小的来历 {#block-size}

$Q$ 沿序列维切成 $T_r = \lceil N/B_r \rceil$ 块，$K, V$ 切成 $T_c = \lceil N/B_c \rceil$ 块。论文 Algorithm 1 取：

$$
B_c = \left\lceil \frac{M}{4d} \right\rceil, \qquad B_r = \min\left(\left\lceil \frac{M}{4d} \right\rceil, d\right)
$$

其中 $M$ 是 SRAM 能放下的元素个数。这个式子里的 4 和 min 都来自同一个要求：一个 Tile 用到的张量要能同时待在片上。论文的证明列了三个约束：

| 张量 | 大小 | 约束 |
| --- | --- | --- |
| $K_j, V_j$ | $B_c \times d$ | $B_c d = O(M)$ |
| $Q_i, O_i$ | $B_r \times d$ | $B_r d = O(M)$ |
| $S_{ij}$ | $B_r \times B_c$ | $B_r B_c = O(M)$ |

前两个约束给出 $B_c$ 和 $B_r$ 都是 $O(M/d)$。为了让外循环尽量少，$B_c$ 取到上限 $\Theta(M/d)$。把它代入第三个约束，就得到 $B_r = O(M/B_c) = O(d)$。所以 $B_r$ 和 $d$ 取 min 的原因，是 $S_{ij}$ 也得放得下，它和 Online Softmax 的统计量没有关系。4 是 $Q, O, K, V$ 四个张量平分 SRAM。

下面代入 $M = 98304$，也就是 192 KB 按 FP16 折算：

| $d$ | $B_c$ | $B_r$ | $S_{ij}$ | 全部张量合计 | 占 $M$ |
| --- | --- | --- | --- | --- | --- |
| 32 | 768 | 32 | 24576 | 75840 | 77.1% |
| 64 | 384 | 64 | 24576 | 82048 | 83.5% |
| 128 | 192 | 128 | 24576 | 106752 | 108.6% |
| 256 | 96 | 96 | 9216 | 107712 | 109.6% |

表里有两点值得注意。第一，只要 $B_r = d$，$S_{ij}$ 就恰好等于 $M/4$，不能当成小量忽略。第二，$d = 128$ 时合计超过了 $M$。这不是算错了：论文的证明只用 $\Theta$ 记号，公式保证的是量级，并不保证常数上真的放得下。写 Kernel 时要按实际占用来定块大小。

另外，192 KB 是 A100 上 L1、纹理缓存和共享内存的合计容量。按 [Ampere 调优指南](https://docs.nvidia.com/cuda/ampere-tuning-guide/index.html#unified-shared-memory-l1-texture-cache)，单个 Block 最多能用 163 KB，所以 $M = 98304$ 是偏乐观的取值。下文的实验可以切换这两个数。

这是论文的抽象模型。[官方 v1.0.9 的 C++ 内核](https://github.com/Dao-AILab/flash-attention/tree/v1.0.9/csrc/flash_attn/src)并不完全照此分配：d = 64 时用 $B_r = 16$、$B_c = 128$ 或 256，d = 128 时用 $B_r = 16$、$B_c = 128$（见 `fmha_fwd_hdim64.cu` 和 `fmha_fwd_hdim128.cu`）。它还通过 `K_IN_REGS`、`V_IN_REGS` 把 K、V 留在寄存器，并让它们共用一块共享内存缓冲。论文说的 on-chip SRAM 在这里相当于寄存器和共享内存合起来，所以不要把上面的公式当成官方配置。FlashAttention-2 论文也提到，块大小实际上要按寄存器和共享内存的情况调，一般取 64 或 128。

### 循环顺序 {#loops}

V1 的外循环遍历 K/V 块，内循环遍历 Q 块：

```python
for j in range(T_c):             # 外循环：K/V
    load(K[j], V[j])             # 从 HBM 读，整个内循环常驻
    for i in range(T_r):         # 内循环：Q
        load(Q[i], O[i], m[i], l[i])
        update_on_chip(i, j)     # 片上计算 S_ij，更新统计量和输出
        store(O[i], m[i], l[i])  # 写回 HBM
```

每个 K/V 块只读一次，代价是每走一步外循环，所有 $Q$ 和 $O$ 都要过一遍 HBM。这个结构直接决定了读写量，也是 [V2](./v2#loop) 把循环顺序调换过来的原因。

## 前向传播 {#forward}

设第 $j$ 轮处理到第 $i$ 个 Q 块，一个 Tile 分五步：

$$
S_{ij} = Q_i K_j^\top / \sqrt{d} \in \mathbb{R}^{B_r \times B_c}
$$

$$
\tilde{m}_{ij} = \text{rowmax}(S_{ij}), \qquad m_i^{\text{new}} = \max(m_i, \tilde{m}_{ij})
$$

$$
\alpha = e^{m_i - m_i^{\text{new}}}
$$

$$
\ell_i^{\text{new}} = \alpha \ell_i + \text{rowsum}\big(e^{S_{ij} - m_i^{\text{new}}}\big)
$$

$$
O_i^{\text{new}} = \frac{\alpha \ell_i}{\ell_i^{\text{new}}} O_i + \frac{1}{\ell_i^{\text{new}}} e^{S_{ij} - m_i^{\text{new}}} V_j
$$

$\alpha$ 把旧统计量换到新最大值的基准下。论文写成先算 $\tilde{P}_{ij} = e^{S_{ij} - \tilde{m}_{ij}}$，再乘 $e^{\tilde{m}_{ij} - m_i^{\text{new}}}$，两者相等。写成代码如下，其中 `unsqueeze(1)` 只表示给一维张量加一个列维度：

```python
# FlashAttention V1 前向传播伪代码
def flash_attention_forward(Q, K, V, B_r, B_c):
    N, d = Q.shape
    O = zeros(N, d)
    m = full(N, -FLT_MAX)  # 行最大值，不用 -inf，原因见“边界情况”
    l = zeros(N)        # 行指数和

    # 外循环：遍历 K/V 块
    for j in range(0, N, B_c):
        K_j = K[j:j+B_c]  # 从 HBM 加载
        V_j = V[j:j+B_c]  # 从 HBM 加载

        # 内循环：遍历 Q 块
        for i in range(0, N, B_r):
            Q_i = Q[i:i+B_r]          # 从 HBM 加载
            O_i = O[i:i+B_r]          # 从 HBM 加载
            m_i = m[i:i+B_r]          # 从 HBM 加载
            l_i = l[i:i+B_r]          # 从 HBM 加载

            # 计算局部注意力分数
            S_ij = Q_i @ K_j.T / sqrt(d)  # [B_r, B_c]

            # 更新统计量
            m_new = max(m_i, rowmax(S_ij))
            l_new = l_i * exp(m_i - m_new) + rowsum(exp(S_ij - m_new))
            l_safe = where(l_new > 0, l_new, 1)  # 该行至今全被屏蔽时，避免 0/0

            # 更新输出
            O_new = O_i * (l_i * exp(m_i - m_new) / l_safe).unsqueeze(1)
            O_new += (exp(S_ij - m_new) / l_safe.unsqueeze(1)) @ V_j

            # 写回 HBM
            O[i:i+B_r] = O_new
            m[i:i+B_r] = m_new
            l[i:i+B_r] = l_new

    return O
```

我们用 NumPy 按这段伪代码逐行实现，取 8 组 $N, d, B_r, B_c$，包括 $N$ 不能被块大小整除的情况，和直接计算 $\text{softmax}(QK^\top/\sqrt{d})V$ 对比。float64 的最大逐元素误差不超过 $1.4 \times 10^{-15}$，float32 不超过 $3.8 \times 10^{-7}$，都是舍入误差的量级。

### 边界情况 {#edge}

论文 Algorithm 1 的初值是 $m = -\infty$、$\ell = 0$。这个初值在没有外部 mask 时没有问题，一旦某一行在第一块就被整块屏蔽，就会出 NaN。上面的代码因此把初值改成了 `-FLT_MAX`，并加了 `l_safe`。下表是按页面代码用 FP32 模拟的结果：

| 情况 | 发生了什么 | 结果 |
| --- | --- | --- |
| 第一轮，该行有未屏蔽的列 | $m_i - m_i^{\text{new}}$ 是极大的负数，$\alpha = 0$，$\ell_i = 0$ | 旧值系数为 0，退化成普通累加 |
| K/V 尾块不足 $B_c$，越界列掩为 $-\infty$ | $e^{-\infty} = 0$，这些列不贡献分母和输出 | 与直接计算一致 |
| K/V 尾块不足 $B_c$，越界列不掩，分数为 0 | 假的 0 进入分母 | 输出错误，最大误差约 $3 \times 10^{-3}$ |
| Q 越界行 | Q 补 0，有效列的分数是 0，$m_i^{\text{new}} = 0$ | 没有 NaN，写回时也被 `q_mask` 挡住 |
| 某行在后面的 K/V 块被整块屏蔽 | $\alpha = 1$，$p = 0$，统计量和输出不变 | 正确 |
| 某行在第一块被整块屏蔽，初值 $-\infty$ | $-\infty - (-\infty)$ 得 NaN，$\alpha$、$p$、$\ell$ 全是 NaN | 该行永远是 NaN |
| 同上，只把初值换成 `-FLT_MAX` | $\alpha = 1$、$p = 0$，但 $\ell_i^{\text{new}} = 0$，算 $O$ 时是 $0/0$ | 该行仍是 NaN，这次进的是 $O$ |
| 同上，`-FLT_MAX` 加 `l_safe` | $\ell = 0$、$O = 0$，下一块正常累加 | 没有 NaN，最大误差约 $2 \times 10^{-7}$ |

第六行最容易被低估：NaN 不会随着后面的有效块消失。下一块 $m_i^{\text{new}}$ 已经有限，$\alpha$ 恢复成 0，可是 $\ell_i$ 里已经存了 NaN，而 $0 \times \text{NaN}$ 还是 NaN。模拟里某行前两块被屏蔽后，后面五块都有效，$\ell$ 依然一路是 NaN。

只看页面上的 mask，这条路径走不到：`kv_mask` 每块至少有一列有效，所以修改前的代码在只有尾块的情况下，NaN 行数也是 0。一旦加上论文 Algorithm 2 那样的 mask，比如左填充的 padding mask，又长过一个 $B_c$，它就会触发。Causal Mask 不会触发，因为每行的第 0 列总是有效。

和 [Online Softmax](../softmax/online-softmax#fix) 相比，这里多了一步。那边换掉初值就够了，因为输出在全部规约完才算一次。这里每个 Tile 都要算一次 $O$，只要前面的块全被屏蔽，这一步就是 $0/0$，所以还要 `l_safe`。官方内核的做法类似，也是对 $\ell$ 判断：`p_sum_log = (sum == 0.f || sum != sum) ? -INFINITY : ...`，以及 `inv_sum = (sum == 0.f || sum != sum) ? 1.f : 1.f / sum`。一整行都被屏蔽时，上面的代码输出全 0，反向用 $e^{S - m}/\ell$ 恢复 $P$ 时同样要判断 $\ell = 0$。

除此之外，减去最大值确实保证了指数的参数都不大于 0，修正因子都不大于 1，因此不会上溢。把分数放大到几千，直接 `exp(S)` 在 FP32 下已经溢出，分块版本的结果仍然有限。

## IO 分析 {#io}

按算法逐行统计前向的 HBM 读写元素数：

| 张量 | 读写 | 总量 |
| --- | --- | --- |
| $K, V$ | 只读一遍 | $2Nd$ |
| $Q$ | 读 $T_c$ 遍 | $T_c \cdot Nd$ |
| $O$ | 读写各 $T_c$ 遍 | $2T_c \cdot Nd$ |
| $m, \ell$ | 读写各 $T_c$ 遍 | $4T_c \cdot N$ |

合计 $T_c(3Nd + 4N) + 2Nd$，脚本逐步累加的结果与此式完全一致。$B_r$ 根本不出现在式子里，因为不管 Q 怎么切，一遍都要过完所有 $Q$。把 $T_c \approx 4Nd/M$ 代入：

$$
\text{FlashAttention} \approx \frac{12N^2 d^2}{M}, \qquad \text{标准实现} = 4N^2 + 4Nd
$$

这就是论文 Theorem 2 的 $\Theta(N^2d^2/M)$，标准实现是 $\Theta(Nd + N^2)$。定理的适用范围是 $d \le M \le Nd$：$M$ 比 $d$ 还小，连一行都放不下；$M$ 超过 $Nd$，整个输入都在片上，读写量由输入输出决定。

这个模型能对上实测吗？论文 Figure 2 中间的图给出了 $N = 1024$、$d = 64$、16 个 head、batch 64 时前向 HBM 读写量随 $B_c$ 的变化，我们用上式算出来对比：

| $B_c$ | 模型（每元素 2 字节） | 论文图中读数（目测） |
| --- | --- | --- |
| 128 | 3.31 GiB | 约 3.4 GB |
| 256 | 1.78 GiB | 约 1.75 GB |
| 512 | 1.02 GiB | 约 0.95 GB |

### “小得多”成立吗 {#how-much}

论文说典型的 $d$（64 到 128）和 $M$（约 100 KB）下，$d^2$ 比 $M$ 小很多倍，所以读写量小很多倍。$d^2$ 与 $M$ 的比值是这样的：$d = 64$ 时差 24 倍，$d = 128$ 时只差 6 倍。

但渐近式省略了常数。从上面的精确式看，$12d^2/M$ 要小于 $4$ 才划算，也就是 $M > 3d^2$，这时才比标准实现读写得少。

<FigFlashV1Bound />

$d = 128$、$M = 98304$ 时只省了 1.92 倍，离“小得多”还有距离；$d = 64$ 时省 7.29 倍，才接近论文 Figure 2 的 9.2 倍。论文附录 E.5 也观察到，头维度 128 时的加速明显小于头维度 64，并把 T4 上较小的加速归因于更小的 SRAM。这和上图是吻合的。切到 $d = 256$ 可以看到，$M = 98304$ 已经落在交点左边。

### 下界到底证明了什么 {#bound}

常见的说法是“任何精确算法都至少要 $\Omega(N^2d^2/M)$ 次访问，所以 V1 渐近最优”。论文证明的比这弱。Proposition 3 的原文是：不存在一个算法，能对 $[d, Nd]$ 内的所有 $M$ 都做到 $o(N^2d^2/M)$ 次访问。

证明也只用到一个点：取 $M = \Theta(Nd)$，这时 $N^2d^2/M = \Theta(Nd)$，而输入输出本身就有 $Nd$ 量级的元素，至少要读写这么多。也就是图中曲线最右端碰到虚线的那个位置。它没有说中段不能做得更好，论文也明确把按 $M$ 参数化的下界留作以后的工作。所以准确的说法是：不能在整个 $M$ 范围内一致地渐近改进，而不是在每个 $M$ 上都最优。常数也不在讨论范围内，V2 调换循环顺序就是在常数上做文章。

| 1024 | 8.29 ms | 2.55 ms | 3.25 倍 | 3.67 ms | 2.29 ms | 1.60 倍 |
| 2048 | 31.75 ms | 9.56 ms | 3.32 倍 | 13.22 ms | 7.64 ms | 1.73 倍 |

8192 一行的“无结果”，在论文的设置里是显存不足：论文按序列长度逐步增加直到 OOM。这个条件下 PyTorch 在 4096 已用 17024 MB，FlashAttention 只要 836 MB，相差约 20 倍（Table 21）。不过只跑前向且不带 dropout 和 mask 时，PyTorch 在 8192 还能运行（Table 18，67.77 ms）。

## 并行：一个 Block 负责一个 head {#parallel}

分块讲的是单个 $(\text{batch}, \text{head})$ 内部的计算。这些计算怎么摆到 GPU 上，要先分清两层。

<figure class="gpu-fig">
  <div class="gpu-scroll" tabindex="0"><FigFlashV1Grid /></div>
  <figcaption>示意图，按每个 SM 运行一个 Block 绘制。琥珀色格是下一栏展开的那个 Block。batch 为 1、32 个 head 时只有 32 个 Block，这是长序列推理的典型情况。</figcaption>
</figure>

前向的划分是这样的：一个 Thread Block 处理一个 head，共 batch × head 个 Block，每个 Block 内部串行走完全部 K/V 块和 Q 块。这是 [FlashAttention-2 论文](https://arxiv.org/abs/2307.08691) 3.2 节对 V1 的描述，官方代码也是如此：`device_1xN_loop` 在同一个 Block 里循环 `loop_step_idx`。所以“一个 Thread Block 对应外循环的一个 K/V 块”并不成立，K/V 块之间也不能这样拆，因为它们都要更新同一批 $O, m, \ell$。

这样划分的代价是 Block 数只有 batch × head。该论文认为这个数大约在 80 以上时才够用，A100 有 108 个 SM。图中 32 个 Block 只能占约 30% 的 SM。

官方代码后来补了两个缓解手段，都不改变上面的结构：

- 前向的 `num_splits`：grid 变成 $(b, h, \text{num\_splits})$，让不同 Block 负责不同的 Q 块（`for (l = blockIdx.z; l < steps; l += step_stride)`）。代价是每个 Block 都要各读一份 K/V，所以代码注释说分得太多会增加 HBM 读写。
- 反向的 seq-parallel：这里才真正是一个 Block 对应一个 K/V 块（`loop_step_idx = blockIdx.z`），代价是要清零和拷贝一份 `dq_tmp`，由启发式函数决定是否启用。

Block 内部还有 Warp 级的分工：V1 把 K、V 分给 4 个 Warp，Q 所有 Warp 共用，所以需要合并中间结果。这种 “split-K” 方案和循环顺序一起，是 [V2](./v2#warp) 改动的对象。

## 反向传播：重算而不保存 {#backward}

反向传播要 $dQ, dK, dV$。设标量损失对输出的梯度为 $dO$，按链式法则：

$$
dV = P^\top dO, \qquad dP = dO\, V^\top
$$

$$
dS_{ij} = P_{ij}\big(dP_{ij} - D_i\big), \qquad D_i = \sum_j P_{ij} dP_{ij}
$$

$$
dQ = dS\, K / \sqrt{d}, \qquad dK = dS^\top Q / \sqrt{d}
$$

后两式的 $1/\sqrt{d}$ 来自 $S = QK^\top/\sqrt{d}$，论文把它写成缩放常数 $\tau$。

看起来 $D_i$ 要对一整行 $P$ 和 $dP$ 求和，放不进 SRAM。这里有一个关键的恒等式：

$$
D_i = \sum_j P_{ij} \sum_k dO_{ik} V_{jk} = \sum_k dO_{ik} \sum_j P_{ij} V_{jk} = \sum_k dO_{ik} O_{ik}
$$

也就是 $\text{rowsum}(dP \odot P) = \text{rowsum}(dO \odot O)$。一个 $N \times N$ 量级的求和，变成了两个 $N \times d$ 张量的点积，这也是前向要保存 $O$ 的原因之一。

$P_{ij}$ 不用保存，因为前向留下了最终的 $m, \ell$，用它们就能恢复：

$$
P_{ij} = \text{diag}(\ell_i)^{-1} e^{S_{ij} - m_i}
$$

这里必须是最后一轮的 $m, \ell$，不是某一轮中间的。图中每一行都对应论文 Algorithm 4 的一步：

<figure class="gpu-fig">
  <div class="gpu-scroll" tabindex="0"><FigFlashV1Backward /></div>
  <figcaption>一个 Tile 的反向流程，自上而下执行，外层仍是 K/V 块，内层是 Q 块。S、P、dP、dS 都只在片上。如果前向用了 dropout，还要保存随机数生成器状态，反向才能重新生成相同的掩码。</figcaption>
</figure>

```python
# 对应论文 Algorithm 4（省略 dropout 和 mask）
D = rowsum(dO * O)                     # 代替对 dP * P 的求和
for j in range(0, N, B_c):
    K_j, V_j = K[j:j+B_c], V[j:j+B_c]
    dV_j, dK_j = 0, 0
    for i in range(0, N, B_r):
        S_ij = Q[i:i+B_r] @ K_j.T / sqrt(d)
        P_ij = exp(S_ij - m[i:i+B_r]) / l[i:i+B_r]        # 重计算，形状已对齐
        dV_j += P_ij.T @ dO[i:i+B_r]
        dS_ij = P_ij * (dO[i:i+B_r] @ V_j.T - D[i:i+B_r])
        dQ[i:i+B_r] += dS_ij @ K_j / sqrt(d)              # 每个 Tile 读写 HBM
        dK_j += dS_ij.T @ Q[i:i+B_r] / sqrt(d)
    dV[j:j+B_c], dK[j:j+B_c] = dV_j, dK_j                 # 每个 K/V 块写一次
```

这些公式都可以验证。在 $N = 96$、$d = 16$ 的随机输入上，恒等式两边的最大差约 $2 \times 10^{-15}$；$dV, dQ, dK$ 与中心差分的最大差约 $5 \times 10^{-9}$；上面的分块版本与整块计算的最大差约 $7 \times 10^{-16}$。

### 重计算要多花多少 {#recompute-cost}

只数矩阵乘：标准实现前向两次（$QK^\top$ 和 $PV$），反向四次（$dV, dP, dQ, dK$），共六次。FlashAttention 多了一次重算 $QK^\top$。这相当于前向矩阵乘的一半，或者总量的 1/6，约 17%。论文 Figure 2 实测的增幅是 13%，同一量级。

| 收益 | 代价 |
| --- | --- |
| 额外显存从 $O(N^2)$ 降到 $O(N)$ | 多一次 $QK^\top$ 和指数运算 |
| 反向的 HBM 读写同样是 $\Theta(N^2d^2/M)$（Theorem 5） | $dQ$ 每个 Tile 都要读写 |
| 不存在 $N \times N$ 张量，能跑更长序列 | 反向 Kernel 更复杂 |

$\Theta(N^2)$ 变成 $\Theta(N^2d^2/M)$ 的量级优势同样来自不写 $S$ 和 $P$。由于算子本来受内存限制，多出的计算被 HBM 省下的时间盖住了。这就是开头那个矛盾的答案。

## 写成 Kernel {#kernel}

实际输入是 4 维张量，batch 和 head 只是批次维：

| 张量 | 形状 | 说明 |
| --- | --- | --- |
| $Q, K, V, O$ | `[B, H, N, D]` | 最后两维做矩阵运算 |
| $S, P$ | `[B, H, N, N]` | 标准实现才有，分块后只有 `[BLOCK_M, BLOCK_N]` 的片段 |
| `M, L` | `[B, H, N]` | V1 专有，跨外循环保存每行的 $m, \ell$ |

下面的 Triton 代码是教学版，直接对应上面的循环。因为一个 program 的寄存器放不下所有 Q 块的 $m, \ell, O$，它们必须存到 HBM，这也是 `M`、`L` 存在的原因。

```python
import math
import torch
import triton
import triton.language as tl

@triton.jit
def flash_attn_v1_kernel(
    Q, K, V, O,    # [B, H, N, D]
    M, L,          # 行最大值与行指数和
    stride_qb, stride_qh, stride_qn, stride_qd,
    stride_kb, stride_kh, stride_kn, stride_kd,
    stride_vb, stride_vh, stride_vn, stride_vd,
    stride_ob, stride_oh, stride_on, stride_od,
    stride_mb, stride_mh,
    N,
    D: tl.constexpr,        # 注意力头维度（head dimension），即每个 token 的特征长度，用在 scale = 1/sqrt(D)
    BLOCK_M: tl.constexpr,  # Q 块行数 B_r
    BLOCK_N: tl.constexpr,  # K/V 块行数 B_c
    BLOCK_D: tl.constexpr,  # 头维度上加载/计算的块宽度，当D本身就是2的幂时，BLOCK_D==D；否则 BLOCK_D > D，多出来的位置用 mask 屏蔽掉
):
    # ========== V1 并行划分：grid = (batch, head) ==========
    # 每个 program 串行扫完整个 (batch, head) 的所有 K/V 块和 Q 块
    batch_id = tl.program_id(0)
    head_id = tl.program_id(1)

    # 当前 (batch, head) 在各张量上的起始偏移
    qkvo_bh_q = batch_id * stride_qb + head_id * stride_qh
    qkvo_bh_k = batch_id * stride_kb + head_id * stride_kh
    qkvo_bh_v = batch_id * stride_vb + head_id * stride_vh
    qkvo_bh_o = batch_id * stride_ob + head_id * stride_oh
    ml_bh = batch_id * stride_mb + head_id * stride_mh

    d_range = tl.arange(0, BLOCK_D)
    scale = 1.0 / math.sqrt(D)

    # ============ 外循环：遍历 K/V 块（V1 关键设计） ============
    for kv_start in range(0, N, BLOCK_N):
        kv_range = kv_start + tl.arange(0, BLOCK_N)
        kv_mask = kv_range < N

        # K_j, V_j 一次加载，常驻寄存器/SRAM，被所有 Q 块复用
        k = tl.load(K + qkvo_bh_k + kv_range[:, None] * stride_kn + d_range[None, :] * stride_kd,
                    mask=kv_mask[:, None] & (d_range[None, :] < D), other=0.0)
        v = tl.load(V + qkvo_bh_v + kv_range[:, None] * stride_vn + d_range[None, :] * stride_vd,
                    mask=kv_mask[:, None] & (d_range[None, :] < D), other=0.0)

        # ============ 内循环：遍历 Q 块 ============
        for q_start in range(0, N, BLOCK_M):
            q_range = q_start + tl.arange(0, BLOCK_M)
            q_mask = q_range < N

            # 加载 Q_i, O_i, m_i, l_i —— V1 中每个外循环都要从 HBM 重新读
            q = tl.load(Q + qkvo_bh_q + q_range[:, None] * stride_qn + d_range[None, :] * stride_qd,
                        mask=q_mask[:, None] & (d_range[None, :] < D), other=0.0)
            o_i = tl.load(O + qkvo_bh_o + q_range[:, None] * stride_on + d_range[None, :] * stride_od,
                          mask=q_mask[:, None] & (d_range[None, :] < D), other=0.0).to(tl.float32)
            m_i = tl.load(M + ml_bh + q_range, mask=q_mask, other=-3.4028234663852886e38)  # -FLT_MAX
            l_i = tl.load(L + ml_bh + q_range, mask=q_mask, other=0.0)

            # S_ij = Q_i @ K_j^T / sqrt(d)
            s = tl.dot(q, tl.trans(k)) * scale
            # 屏蔽 K/V 越界列，防止假 0 污染 softmax 分母
            s = tl.where(kv_mask[None, :], s, float('-inf'))

            # Online Softmax 更新
            m_new = tl.maximum(m_i, tl.max(s, axis=1))
            alpha = tl.exp(m_i - m_new)
            p = tl.exp(s - m_new[:, None])
            l_new = alpha * l_i + tl.sum(p, axis=1)
            # 该行至今全被屏蔽时 l_new 为 0，避免 0/0
            l_safe = tl.where(l_new > 0, l_new, 1.0)

            # 输出修正 + 累加（与前向传播一节的公式一致）
            o_new = o_i * (alpha * l_i / l_safe)[:, None] \
                    + tl.dot(p.to(v.dtype), v) / l_safe[:, None]

            # 把更新后的 O_i, m_i, l_i 写回 HBM，供下次外循环使用
            tl.store(O + qkvo_bh_o + q_range[:, None] * stride_on + d_range[None, :] * stride_od,
                     o_new.to(O.dtype.element_ty),
                     mask=q_mask[:, None] & (d_range[None, :] < D))
            tl.store(M + ml_bh + q_range, m_new, mask=q_mask)
            tl.store(L + ml_bh + q_range, l_new, mask=q_mask)


def flash_attn_v1(Q, K, V, BLOCK_M=64, BLOCK_N=64):
    # Q, K, V: [B, H, N, D]
    B, H, N, D = Q.shape
    # 中间结果用 FP32：O 要被反复读写，FP16 会累积舍入误差
    O = torch.zeros_like(Q, dtype=torch.float32)
    # 初值不用 -inf：某行第一块被整块屏蔽时，-inf - (-inf) 会得到 NaN
    M = torch.full((B, H, N), -torch.finfo(torch.float32).max, device=Q.device, dtype=torch.float32)
    L = torch.zeros((B, H, N), device=Q.device, dtype=torch.float32)

    BLOCK_D = triton.next_power_of_2(D)
    grid = (B, H)  # V1 并行：仅在 batch×head 维度上
    flash_attn_v1_kernel[grid](
        Q, K, V, O, M, L,
        Q.stride(0), Q.stride(1), Q.stride(2), Q.stride(3),
        K.stride(0), K.stride(1), K.stride(2), K.stride(3),
        V.stride(0), V.stride(1), V.stride(2), V.stride(3),
        O.stride(0), O.stride(1), O.stride(2), O.stride(3),
        M.stride(0), M.stride(1),
        N, D=D, BLOCK_M=BLOCK_M, BLOCK_N=BLOCK_N, BLOCK_D=BLOCK_D,
    )
    return O.to(Q.dtype)
```

用这段代码时要记住以下几点：

- 相对原稿，我们改了两处。一处是[边界情况](#edge)里的 `-FLT_MAX` 和 `l_safe`。另一处是中间 $O$ 用 FP32。按原写法 `O` 与 `Q` 同类型，FP16 输入时每一轮都要舍入一次。模拟中 $N = 4096$、$d = 64$、块大小 64 时，均方根误差从 $5.3 \times 10^{-6}$ 涨到 $3.1 \times 10^{-5}$，最大误差从 $4.6 \times 10^{-5}$ 涨到 $3.5 \times 10^{-4}$。官方内核也是另开一个 FP32 的 `o_tmp`，最后一轮才写回输出。
- `BLOCK_M`、`BLOCK_N` 要是 2 的幂（`tl.arange` 的要求），所以不能直接用论文公式算出的 192 这种值。
- 用 NumPy 逐行还原这段循环，包括 `BLOCK_D > D` 的填充，结果与直接计算的误差约 $10^{-16}$。逻辑是对的。
- 它是教学用的 V1，不是官方代码。官方 V1 是 C++ 内核；官方的 Triton 版本（`flash_attn_triton_og.py`，源自 OpenAI 教程）一开始就是外循环 Q、grid 含 Q 块的结构，也就是 V2 的循环顺序。官方内核还把 $m, \ell$ 合成一个 `softmax_lse` 保存，并把 scale 作为参数传入。

## 小结 {#summary}

| 瓶颈 | 表现 | 做法 |
| --- | --- | --- |
| $S, P$ 写到 HBM | 读写 $4N^2$ 个元素，算术强度只有 $d/2$ | 分块，每次只算一个 Tile |
| softmax 依赖一整行 | 分块后分母未知 | 维护 $m, \ell$，按 Online Softmax 修正 |
| 反向要用 $S, P$ | 保存就要 $O(N^2)$ 显存 | 只存 $m, \ell, O$，反向重算 |
| $D_i$ 要整行求和 | 放不进 SRAM | 换成 $\text{rowsum}(dO \odot O)$ |

代价也很清楚：$Q$ 和 $O$ 要在 HBM 与 SRAM 之间往返 $T_c$ 次，每个 head 只有一个 Block。[FlashAttention V2](./v2) 接着解决这两点。

## 检验一下 {#check}

::: details 思考：d 翻倍、其他不变，前向读写量大约变成几倍？
约 4 倍。$B_c = M/(4d)$ 减半，所以 $T_c$ 翻倍，走的遍数多一倍；每遍要读写 $Nd$ 量级的元素，也翻倍。这对应 $N^2d^2/M$ 里的 $d^2$。在实验里把 $d$ 从 64 切到 128，全程从 17.8 MiB 变成 68.7 MiB，约 3.9 倍，和 4 倍的差距来自 $T_c$ 的取整和 $m, \ell$ 这些低阶项。
:::

::: details 思考：读写量里没有 B_r，那为什么不把 B_r 取得很小，把 SRAM 让给 B_c？
从读写量看确实划算：$Q, O$ 占得少，$B_c$ 就能接近 $M/(2d)$，外循环次数减半。官方内核用的 $B_r = 16$ 就接近这个思路。代价在别处：$B_r$ 越小，内循环次数越多，加载和 softmax 的开销越大，矩阵单元每次能处理的也越少。所以它是实现层面的权衡，论文的渐近分析不会体现出来。
:::

::: details 思考：把循环换成外层 Q、内层 K/V，读写量怎么变？
$Q$ 只读一遍，$O$ 只写一遍，$m, \ell$ 全程在片上，不用写到 HBM。但是 $K, V$ 要读 $T_r$ 遍，读写量约为 $T_r \cdot 2Nd$。它没有改变 $N^2d^2/M$ 这个量级，改的是常数，并且不同 Q 块之间没有依赖，能并行到不同的 Block。两版的逐项对比见 [V2](./v2#traffic)。
:::

::: details 思考：反向时如果用某一轮中间的 m 和 l 恢复 P，会发生什么？
恢复出来的就不是整行的 softmax，分母只覆盖了前几个 K/V 块。每一轮的 $m, \ell$ 只对应当时已经看过的那部分，这也是前向结束时才写最终值的意义。V1 的 M、L 在 HBM 里中途不断被覆盖，反向读到的自然是最后一轮的值。
:::

::: details 思考：实验里 N 从 4096 增加到 8192，比值几乎不变，为什么？
$d = 64$ 时比值从 7.29 变成 7.44。两边都随 $N^2$ 增长：标准实现是 $4N^2$，FlashAttention 是 $12N^2d^2/M$，所以比值约等于 $M/(3d^2)$，也就是 8 倍，差的部分来自取整和低阶项。这个比值由 $M$ 和 $d$ 决定，和序列长度关系不大。
:::
