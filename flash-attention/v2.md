# FlashAttention V2 图解

<p class="gpu-lede">同一张 A100，head dimension 128，序列长度 2048。FlashAttention V1 的前向跑出 71 TFLOPS，V2 跑出 227 TFLOPS，是前者的 3.2 倍。两者的输出完全相同，V2 没有做任何近似。多出来的算力是从哪里来的？</p>

这篇接着 [FlashAttention V1 图解](./v1)往下讲。V1 用分块和 [Online Softmax](../softmax/online-softmax) 把中间矩阵留在了芯片上，这些内容不再重复。本文只回答一个问题：既然 HBM 访问已经省下来了，V1 为什么还是远远够不到矩阵乘的峰值？

答案是三个工作分配上的问题，而不是算法问题。

## V1 卡在哪里 {#bottleneck}

先看 A100 的两个数字。[Tensor Core](../about_gpu/ai-compute#tensor-core) 做 FP16 矩阵乘的峰值是 312 TFLOPS，普通算术单元做 FP32 只有 19.5 TFLOPS。

<div class="gpu-chain">
  <div><b>312 T</b><span>FP16 矩阵乘峰值 FLOP/s</span></div>
  <div><b>19.5 T</b><span>非矩阵乘 FP32 峰值 FLOP/s</span></div>
  <div><b>16 倍</b><span>一个非矩阵乘 FLOP 的相对代价</span></div>
  <div><b>80~90%</b><span>优化过的 GEMM 能达到的峰值占比</span></div>
</div>

[优化过的 GEMM](../gemm/gemm) 能达到峰值的 80~90%。而论文给出的 V1 只有 25~40%：前向 30~50%，反向 25~35%。Attention 的 FLOP 几乎全是矩阵乘，理应接近 GEMM。差距来自下面三处，顺序沿用论文第 3 节，论文没有给出它们各自的贡献占比。

| 问题 | 具体表现 | V2 的做法 |
| --- | --- | --- |
| SM 没用满 | V1 论文方案只沿 batch 和头并行，长序列时 batch 小，Block 数远少于 SM 数 | 调换循环顺序，再沿序列并行 |
| 非矩阵乘太贵 | FLOP 占比很小，但每个贵 16 倍 | 延迟归一化，只留必要的操作 |
| Warp 之间要通信 | 沿 K/V 切分，部分结果经共享内存合并 | 改为沿 Q 切分 |

注意第二行：非矩阵乘的 FLOP 占比并不高。按下文的模型只有 1~2%，它贵在单价，不贵在数量。

## 调换循环顺序 {#loop}

V1 的外循环遍历 K/V 块，内循环遍历 Q 块。V2 反过来，外循环遍历 Q 块，内循环遍历 K/V 块。论文说明，这个调换和沿序列并行最早由 Phil Tillet 在 Triton 的实现中提出并实现。

```python
外循环: for i = 1 to T_r (遍历 Q 块) — 分配给不同 Thread Block
    从 HBM 加载 Q_i 到 SRAM（只加载一次）
    初始化 O_i = 0, m_i = -inf, l_i = 0
    内循环: for j = 1 to T_c (遍历 K/V 块)
        从 HBM 加载 K_j, V_j 到 SRAM
        计算 S_ij，更新统计量和 O_i（全在芯片上）
    将最终 O_i 写回 HBM（只写一次）
```

### 算清这笔账 {#traffic}

调换之后 O 确实省了很多，但 K、V 变多了。把两版的访问次数都写出来：

| 张量 | V1 块访问次数（共） | V2 块访问次数（共） |
| --- | --- | --- |
| Q 读 | $T_r T_c$ | $T_r$ |
| K 读 | $T_c$ | $T_r T_c$ |
| V 读 | $T_c$ | $T_r T_c$ |
| O 读 | $T_r T_c$ | 0 |
| O 写 | $T_r T_c$ | $T_r$ |
| 统计量读 | $2 T_r T_c$（m、l） | 0 |
| 统计量写 | $2 T_r T_c$（m、l） | $T_r$（L） |

常说的“O 的访问从 $2T_c$ 次降到 1 次”是**每个 Q 块**的口径：V1 中每个 $O_i$ 被读写 $2T_c$ 次，V2 中只写 1 次。按总量算是从 $2T_rT_c$ 降到 $T_r$。

如果忽略很小的统计量，以 $N \cdot d$ 个元素为单位，两版的总量分别是：

$$
\text{V1} = 3T_c + 2, \qquad \text{V2} = 2T_r + 2
$$

V2 比 V1 省多少，取决于 $T_r$ 和 $T_c$ 的比例。动手试试：

<FlashV2Lab />

默认的 $N = 8192$、$d = 128$、$T_r = T_c = 64$ 下，从 V1 到 V2 的变化如下：

| 张量 | V1（MB） | V2（MB） | 变化（MB） |
| --- | --- | --- | --- |
| O 读写 | 268.4 | 2.1 | 省 266.3 |
| K、V 读 | 4.2 | 268.4 | 多 264.2 |
| Q 读 | 134.2 | 2.1 | 省 132.1 |
| 统计量读写 | 8.4 | 0.03 | 省 8.4 |
| 合计 | 415.2 | 272.7 | 省 142.5，降到 66% |

这张表说明两件事。第一，O 省下的量几乎被 K、V 多读的量抵消了，两者只差 2.1 MB，正好是一份 O。所以“减少 O 的读写比增加 K、V 的读取收益更大”并不是净收益的来源，净收益主要来自 Q 不用再反复读取。

第二，这个收益不是无条件的。假设两版用同样的块大小，把 $T_r$ 拖到 128、$T_c$ 留在 64，V2 反而比 V1 多搬 30%。反过来，$T_r = 64$、$T_c = 128$ 时，V2 只有 V1 的 33%。官方实现在 A100 上用的正是后一类配置：head dim 128 时 $B_r = 128$、$B_c = 64$。

还要注意，这张表没有建模 L2 缓存。K、V 是只读的，又被不同 Block 反复读取，实际可能命中 L2，论文也明确只讨论 HBM 和 SRAM。而且论文并没有用 HBM 流量解释这次调换，它给出的理由是下一节的并行度。

### Thread Block 与 Q 块 {#parallel}

Q 块之间完全独立：每个 Q 块只计算自己那些行的输出，既不依赖别的 Q 块，也不写别人的结果。所以外循环可以直接交给 [Grid](../about_gpu/gpu#grid)。官方实现的写法非常直接：

```cpp
const int num_m_block = (params.seqlen_q + kBlockM - 1) / kBlockM;
dim3 grid(num_m_block, params.b, params.h);   // Grid 的 x 维就是 Q 块的序号
// Kernel 里：const int m_block = blockIdx.x;
```

论文认为，Block 数在 80 个以上时，A100 的 108 个 SM 才能基本用满。序列一长，batch 通常变小，只沿 batch 和头并行就不够了。V2 再乘上一个 $T_r$，Block 数一下就上去了。

官方实现还留了一个编译期开关 `Is_Q_in_regs`，可以把 Q 放进寄存器。不过当前 A100 用的模板都把它设为 `false`，和论文算法一致：Q 在共享内存里。

::: details 思考：V1 的外循环不能并行，内循环的 Q 块总可以吧？
可以，而且 V1 的公开实现后来确实这样做了。v1.0.9 的 Grid 是 `(b, h, num_splits)`，第三维把 Q 块按取模分给多个 Block，`num_splits` 由启发式规则设定，上限是 30。代码注释特意指出，各步处理的行号必须对齐，否则 Block 之间会产生依赖。

这可能也解释了一个现象：论文图 5(b) 中，V1 在 16k 序列（1 个 batch、16 个头）上仍有 73 TFLOPS，高于 16/108 个 SM 对应的 46 TFLOPS。论文没有说明测试用的版本，所以这只是推测。论文第 3.2 节说的“V1 只沿 batch 和头并行”，是对第一版方案的概括。V2 把序列维度放到外循环，并行就成了结构本身的一部分。
:::

::: details 思考：如果 K、V 每次都真的走 HBM，搬运和计算哪个先到头？
还是 $N = 8192$、$d = 128$、$T_r = T_c = 64$。矩阵乘的 FLOP 是 $4N^2d \approx 34.4$ G，在 312 TFLOPS 下至少要 110 μs。V1 要搬 415 MB，在 2039 GB/s 下至少要 204 μs，已经比计算慢。V2 要搬 273 MB，至少要 134 μs，还是更慢。

也就是说，如果完全没有 L2 命中，这份工作会先被[带宽那条线](../about_gpu/ai-compute#roofline)压住。这是上界估算，不是测量值。论文测得 V2 在这组条件下为 224 TFLOPS，也就是 153 μs，如果全走 HBM，折算相当于约 1.8 TB/s。所以这笔账至少提醒我们，块大小和 L2 命中都不能忽略。
:::

## 延迟归一化 {#deferred}

第二个瓶颈是非矩阵乘运算。一个 Tile 里除了 $QK^\top$ 和 $\tilde{P}V$，还有减最大值、求指数、行求和和各种缩放。

### 不用每步都归一化 {#defer-math}

V1 每个 Tile 都维持一个已经归一化的 $O$：

$$
O_i^{(j)} = \frac{l_i^{(j-1)} \cdot e^{m_i^{(j-1)} - m_i^{(j)}}}{l_i^{(j)}} \cdot O_i^{(j-1)} + \frac{e^{S_{ij} - m_i^{(j)}}}{l_i^{(j)}} \cdot V_j
$$

但是归一化的结果只有最后才用得到，中间状态没人读。于是 V2 只维护未归一化的累积：

$$
\tilde{O}_i^{(j)} = e^{m_i^{(j-1)} - m_i^{(j)}} \cdot \tilde{O}_i^{(j-1)} + e^{S_{ij} - m_i^{(j)}} \cdot V_j
$$

等内循环结束，再一次性除掉：

$$
O_i = \tilde{O}_i^{(T_c)} / l_i^{(T_c)}
$$

两者等价的原因很简单：对每一步都有 $O_i^{(j)} = \tilde{O}_i^{(j)} / l_i^{(j)}$。用数值实验也能确认：1200 组 $(N, B_r, B_c)$ 下，无论有没有 Causal Mask，下文的 V2 伪代码都和直接计算一致，$O$ 和 $L$ 的最大误差约 $1.8 \times 10^{-15}$，也没有出现 NaN。逐个 Tile 比较 $\tilde{O}/l$ 和逐步归一化的 V1，最大误差约 $1.3 \times 10^{-15}$。

这里的 V1 要加一个保护。V1 论文的算法先用局部最大值 $\tilde{m} = \text{rowmax}(S)$ 算 $\tilde{P}$，如果某一行在当前块被整块屏蔽，$\tilde{m}$ 就是 $-\infty$，$S - \tilde{m}$ 得到 NaN。按字面实现时，Causal 场景下 1200 组里有 539 组出 NaN。V2 直接减 $m^{\text{new}}$，没有这条路径，[V1 页的代码](./v1#forward)用的也是 $m^{\text{new}}$。

### 内循环还剩什么 {#inner}

<figure class="gpu-fig">
  <div class="gpu-scroll" tabindex="0"><FigFlashV2Inner /></div>
  <figcaption>FLOP 数按论文的计法，一次矩阵乘 2BrBcd，指数记 1 个 FLOP。V1 一栏按上面的公式把两项分开写，所以是 1 乘 2 除。</figcaption>
</figure>

常说的“少了 2 除 1 乘”，是按上面的公式分开写的计数。V1 论文 Algorithm 1 第 12 行实际提了公因子：

$$
O_i \leftarrow \text{diag}(l^{\text{new}})^{-1}\big(\text{diag}(l)\, e^{m - m^{\text{new}}} O_i + e^{\tilde{m} - m^{\text{new}}} \tilde{P} V_j\big)
$$

这样写是 1 除 1 乘，再加一个新项的指数缩放，同样是三步，只是组成不同。

更重要的是，**删掉的只是三个 $B_r d$ 级别的操作**。内循环里仍然留着这些非矩阵乘：

- `rowmax`，以及和 $m$ 取最大值。
- $S - m^{\text{new}}$ 和 $\exp(\cdot)$，各 $B_rB_c$ 次，这才是大头。
- `rowsum`，以及 $l$ 的指数缩放和累加。
- 旧 $\tilde{O}$ 的指数缩放，$B_r d$ 次。

能省多少可以算一下。假设矩阵乘的单价是 1/312，其他 FLOP 的单价是 1/19.5：

| $B_r \times B_c$，$d$ | 非矩阵乘占 FLOP | 非矩阵乘占时间 | 单 Tile 耗时比 V2/V1 | FLOP/s 上限 |
| --- | --- | --- | --- | --- |
| 128 × 128，64 | 2.30% → 1.74% | 27.4% → 22.1% | 0.93 | 232 → 247 T |
| 128 × 64，128 | 2.30% → 1.17% | 27.4% → 15.9% | 0.86 | 232 → 265 T |
| 128 × 128，128 | 1.54% → 0.97% | 20.1% → 13.6% | 0.93 | 253 → 272 T |

表中的箭头都是 V1 → V2。这个模型很粗糙，例如指数实际比一次乘法贵，所以它只给出量级。但量级已经够说明问题：延迟归一化本身最多省 7~14% 的时间，单靠它解释不了 3 倍的提速。V2 的上限 247、265 T 分别高于论文测得的 193、227 T，也说明这个模型没有把上限算低。

论文的第二个小改动顺手把统计量也省了：不保存 $m$ 和 $l$，只保存 $L_i = m_i + \log l_i$，也就是每行的 logsumexp。反向传播用 $P_{ij} = \exp(S_{ij} - L_i)$ 就能恢复 $P$，见[后文](#backward)。

## Warp 级工作分配 {#warp}

第三个瓶颈在一个 Thread Block 内部：4 个 Warp 怎么分一个 Tile？V1 沿 K/V 切，这是 FlashAttention-2 论文第 3.3 节和图 3 的明确说法，称为 split-K。V1 论文本身没有讨论 Warp，但 v1.0.9 的实现也能印证：它把 O 的中间结果存到共享内存再同步。

<figure class="gpu-fig">
  <div class="gpu-scroll" tabindex="0"><FigFlashV2Warp /></div>
  <figcaption>按论文图 3 重画并补上输出。琥珀色是所有 Warp 都要访问的数据，青色是分给各 Warp 的部分。这里只表示工作怎么分：论文的算法把 Q、K、V 都载入 SRAM。论文给出的是 4 个 Warp 的情况，实际常用 4 或 8 个。</figcaption>
</figure>

沿 K/V 切时，每个 Warp 只有 $S$ 的若干列。softmax 的归一化是按行做的，一行偏偏分散在 4 个 Warp 中，所以 row-max、row-sum 要合并，$PV$ 的部分结果也要合并。论文指出，这些结果要写到共享内存、同步、再相加，正是这些读写拖慢了 V1。

沿 Q 切时，每个 Warp 拥有若干完整的行，一行的所有数据都在同一个 Warp 内，输出也是它独占的。

| 对比项 | 沿 K/V 切（V1） | 沿 Q 切（V2） |
| --- | --- | --- |
| 所有 Warp 都要访问 | Q | K、V |
| 每个 Warp 算出 | $S$ 的若干列 | $S$ 的若干行 |
| Softmax | 要合并部分结果 | 本 Warp 内完成 |
| 输出 $O$ | 同一行由多个 Warp 累加 | 每行只属于一个 Warp |

这里的“不用通信”，指的是不用合并结果。Warp 之间并非完全没有同步：K、V 块要用异步拷贝载入共享内存，官方实现的前向循环里每次都有 `cp_async_wait` 和 `__syncthreads`。

Warp 数和块大小都是手工调出来的。官方代码里有几条注释记录了实测结果：head dim 64 时，用 8 个 Warp 慢 18%，用 2 个慢 5%；块大小 64 × 256 慢 27%，256 × 64 因为寄存器溢出慢 85%。这些数字我们没有复测，但它们说明了一件事：块越大，访存越少，但寄存器和共享内存也越紧张。论文最终选的是 $\{64, 128\} \times \{64, 128\}$。

## Causal Mask {#causal}

自回归模型中，第 $i$ 个 token 只能看到自己和之前的 token，所以 $S_{ij}$ 在 $j > i$ 时要被置为 $-\infty$。这些元素经过 $\exp$ 后变成 0，对结果毫无贡献。把它们算出来再丢掉，就白白浪费了将近一半的矩阵乘。

已经按块计算了，自然可以按块跳过。这不是 V2 才有的优化：论文说明 FlashAttention 和 FlashAttention-2 都能这样做，v1.0.9 的实现里也有对应的 `begin` 计算。

### 三种块 {#tile-kinds}

设一个 Tile 的实际行范围是 $[r_{\min}, r_{\max}]$，列范围是 $[c_{\min}, c_{\max}]$：

| 类型 | 条件 | 处理 |
| --- | --- | --- |
| 完整 | $r_{\min} \ge c_{\max}$ | 正常计算，不用 mask |
| 跳过 | $r_{\max} < c_{\min}$ | 连 K、V 都不读 |
| 部分 | 其他 | 计算后逐元素 mask |

### 边界都对吗 {#causal-edge}

我们枚举了 129 种 $N$ 和 100 种 $(B_r, B_c)$ 组合，共 528 万个 Tile，把每个 Tile 的分类和逐元素判断比较。另外用 1200 组参数让带 mask 的分块结果与直接计算对比，没有 NaN，最大误差约 $1.8 \times 10^{-15}$。结论如下：

- 跳过条件和“部分”判断都不会漏。不存在该 mask 却没有 mask，或者该算却被跳过的 Tile。
- 内循环的上界 `kv_end = min(N, i + B_r)` 足够。`range(0, kv_end, B_c)` 访问的块，恰好就是含有可见元素的块，`min` 则防止读到序列之外。
- 按名义块大小判断“完整”只会偏保守。例如 $N = 10$、$B_r = 3$、$B_c = 4$，第 3 个 Q 块只有第 9 行，第 2 个 K 块只有第 8、9 列，它其实完整，但名义最大列是 11，所以被当成部分。多做一次 mask 不影响结果，528 万个 Tile 里有 2718 个这种情况。

每个 Q 块有几个部分 Tile？序列长度是块大小的倍数、两个块大小也成倍数时，最多 $\lceil B_r / B_c \rceil$ 个，$B_r = B_c$ 时就是论文说的 1 个。这正是官方实现的 `n_masking_steps`。两个块大小不成倍数时可能更多，例如 $B_r = 5$、$B_c = 7$ 时是 2 个。序列长度不是块大小的倍数时，官方代码也会多算 1 步，它的注释说明序列可能在块的中间结束。

官方实现还有一个细节：内循环从大的块号往小走，先处理要 mask 的块，后面的循环就能省掉 mask 的分支。代价是一行碰到的第一个块可能全被屏蔽，这要求有 K 块的起点落在 Q 块内部，比如 A100 上 head dim 128 用的 $128 \times 64$。`softmax.h` 里的 `Check_inf` 正是在防这个问题，详见[下文](#inf)。下面的伪代码从小往大走，第一个块总含第 0 列，不会碰到这种情况。

### 能省多少 {#causal-speed}

块数占比取决于块有多大：$T$ 行 $T$ 列的方块要处理 $T(T+1)/2$ 个 Tile。

| $N$（$B = 128$） | 处理的 Tile 占比 | 按块数算的提速上限 |
| --- | --- | --- |
| 512 | 62.5% | 1.60 倍 |
| 1024 | 56.3% | 1.78 倍 |
| 2048 | 53.1% | 1.88 倍 |
| 8192 | 50.8% | 1.97 倍 |

论文报告的实际提速约 1.7~1.8 倍，和这个量级一致。序列越短，对角线上的块占比越高，越达不到 2 倍。

## 前向完整算法 {#forward}

把上面三点合起来，就是前向传播的完整伪代码。下面的版本用 numpy 实际跑过（把 `parallel for` 换成普通循环）。

```python
def flash_attention_v2_forward(Q, K, V, B_r, B_c, causal=False):
    N, d = Q.shape
    O = zeros(N, d)
    L = zeros(N)  # logsumexp，用于反向传播

    # 外循环（并行化到不同 Thread Block）
    parallel for i in range(0, N, B_r):
        Q_i = Q[i:i+B_r]  # 加载到 SRAM，整个内循环驻留
        n_i = Q_i.shape[0]  # 最后一个 Q 块可能不足 B_r 行

        # 初始化累积量（官方实现放在寄存器）
        m_i = full(n_i, -inf)
        l_i = zeros(n_i)
        O_tilde = zeros(n_i, d)  # 未归一化的累积输出

        # 内循环：遍历 K/V 块
        kv_end = min(N, i + B_r) if causal else N
        for j in range(0, kv_end, B_c):
            K_j = K[j:j+B_c]  # 从 HBM 加载
            V_j = V[j:j+B_c]  # 从 HBM 加载

            # 计算局部注意力分数
            S_ij = Q_i @ K_j.T / sqrt(d)

            # 应用 causal mask（仅跨对角线的块需要）
            # i, j 已是绝对起始坐标：K 块最大列号 > Q 块最小行号时才可能有屏蔽
            if causal and i < j + B_c - 1:
                # 把行号 < 列号的元素置为 -inf
                apply_causal_mask(S_ij, i, j)

            # 更新统计量
            m_new = max(m_i, rowmax(S_ij))
            P_ij = exp(S_ij - m_new[:, None])
            l_new = exp(m_i - m_new) * l_i + rowsum(P_ij)

            # 更新未归一化输出
            O_tilde = exp(m_i - m_new)[:, None] * O_tilde + P_ij @ V_j

            m_i = m_new
            l_i = l_new

        # 最终归一化并写回
        O[i:i+B_r] = O_tilde / l_i[:, None]
        L[i:i+B_r] = m_i + log(l_i)  # 保存 logsumexp 给反向

    return O, L
```

和 V1 对比如下：

| 方面 | V1 | V2 |
| --- | --- | --- |
| 外循环 | K/V 块 | Q 块（并行） |
| 每个 O 块的 HBM 访问 | $2T_c$ 次（$T_c$ 读 + $T_c$ 写） | 1 次（仅最终写回） |
| 每个 K/V 块的 HBM 读取 | 1 次 | $T_r$ 次，反而更多 |
| 内循环归一化 | 每步反归一化再归一化 | 只做指数缩放，最后统一除一次 |
| Warp 切分维度 | 沿 K/V（split-K，要合并结果） | 沿 Q（每 Warp 独占若干行） |
| Causal 块级跳过 | 有 | 有 |
| 保存的统计量 | $m$ 和 $l$ | $L = m + \log l$ |

### 初值 −∞ 什么时候出 NaN {#inf}

伪代码沿用论文 Algorithm 1 第 5 行的初值 $m = -\infty$、$l = 0$。危险只有一种：某一行直到当前块都没见过可见元素，$m_i$ 和 $m^{\text{new}}$ 同时是 $-\infty$。这时 $-\infty - (-\infty)$ 得 NaN，而 $0 \times \text{NaN}$ 还是 NaN，所以 $l = 0$ 救不了它。NaN 进了 $l$ 和 $\tilde{O}$ 就不会消失：一行前 2 个块被屏蔽、后 6 个块有效，最后输出仍是 NaN。

下表是实际跑出来的结果。第一、二行用 FP64 枚举 1200 组 $(N, B_r, B_c)$，其余行用 FP32 枚举 144~180 组。

| K/V 顺序和 mask | 初值 | 结果 |
| --- | --- | --- |
| 本页伪代码：从小到大，Causal | $-\infty$ | 没有 NaN。整块屏蔽发生了 55785 行次，都在第一块之后，此时 $m^{\text{new}} = m$，缩放系数为 1，$\tilde{P}$ 为 0 |
| 从大到小（539 组）或乱序（421 组），Causal | $-\infty$ | 出 NaN。从大到小时，当且仅当有 K 块起点落在 Q 块内部，1200 组预测无一不符 |
| 从大到小，Causal | `-FLT_MAX` | 没有 NaN，误差约 $5 \times 10^{-7}$ |
| 左填充超过一个 $B_c$，每行仍有可见列 | $-\infty$ | 144 组全部出 NaN，每一行都是 NaN |
| 同上 | `-FLT_MAX` | 没有 NaN，误差约 $8 \times 10^{-7}$ |
| 左填充加 Causal，有的行什么都看不到 | `-FLT_MAX` | 只有这些行出 NaN，来自最后的 $0/0$ |
| 同上 | `-FLT_MAX`，最后除以 `l_safe` | 没有 NaN，这些行输出 0 |

所以本页的伪代码在 Causal 下是对的，不用改。如果要接 padding mask，或者改变遍历顺序，只需要改两处：

```python
m_i = full(n_i, -FLT_MAX)              # 不用 -inf
# ……内循环不变……
l_safe = where(l_i > 0, l_i, 1)        # 只在循环结束后判断一次
O[i:i+B_r] = O_tilde / l_safe[:, None]
L[i:i+B_r] = m_i + log(l_safe)
```

这和 [V1 页的边界情况](./v1#edge)结论不同，原因正是延迟归一化。V1 每个 Tile 都要除以 $l$，只换初值还是会在循环里遇到 $0/0$，所以 `l_safe` 要放进循环。V2 的内循环不做除法，只换初值就够了，`l_safe` 只为“整行都不可见”这一种情况兜底。

官方实现选了另一种写法，效果相同：`Check_inf` 在 `row_max` 为 $-\infty$ 时把它当 0 来算缩放系数，`normalize_softmax_lse` 在 `sum == 0` 时用 `inv_sum = 1`，并在普通前向中把这一行的 LSE 记为 `INFINITY`，按 $P = \exp(S - L)$ 算就是 0。对除法的保护同样只在归一化时做一次。

## 反向传播 {#backward}

### 外循环是 K/V，方向和前向相反 {#bwd-loop}

前向的外循环是 Q，反向的外循环却是 K/V。这一点 V1 和 V2 相同，FlashAttention-2 论文说 V2 的反向和 V1“几乎一样”。原因看输出就明白了：每个 Thread Block 负责一个列块时，$dK_j$ 和 $dV_j$ 只有它一个写者，可以留在 SRAM 里累积，最后写回一次。

代价落在 $dQ$ 上：一个 $dQ_i$ 要接收所有列块的贡献。

  <div class="gpu-scroll" tabindex="0"><FigFlashV2Backward /></div>
  <figcaption>依据论文图 2 和 Algorithm 2 重画，并补上预处理 Kernel。这是唯一需要跨 Block 通信的地方：论文指出，不同列块之间共享的计算只有更新 dQ。</figcaption>
</figure>

论文 Algorithm 2 的写法是把 $dQ_i$ 读入 SRAM、更新后写回，第 3.2 节说明并行时用原子加。官方实现里，每个 Block 对一个 FP32 的 `dQ_accum` 缓冲区做 `atomicAdd`，最后由一个转换 Kernel 写成 $dQ$。如果要求结果确定，每个 Block 写自己的缓冲区，由转换 Kernel 统一求和，这样加法顺序就固定了。

```python
D = rowsum(dO * O)                    # 预处理，写入 HBM
parallel for j in range(0, N, B_c):   # 每个列块一个 Thread Block
    K_j, V_j = K[j:j+B_c], V[j:j+B_c]
    dK_j, dV_j = zeros_like(K_j), zeros_like(V_j)
    for i in range(0, N, B_r):        # Q_i、dO_i、L_i、D_i 是第 i 块的切片
        S_ij = Q_i @ K_j.T / sqrt(d)  # Causal 时同样跳过或 mask
        P_ij = exp(S_ij - L_i[:, None])
        dV_j += P_ij.T @ dO_i
        dP_ij = dO_i @ V_j.T
        dS_ij = P_ij * (dP_ij - D_i[:, None])
        atomic_add(dQ_i, dS_ij @ K_j / sqrt(d))
        dK_j += dS_ij.T @ Q_i / sqrt(d)
    dK[j:j+B_c], dV[j:j+B_c] = dK_j, dV_j
```

和前向不同，Warp 切分虽然同样避开 split-K，但论文说仍然需要一些同步，因为 $Q, K, V, O, dO, dQ, dK, dV$ 之间的依赖更复杂。反向的代码也更长：5 次矩阵乘要放下的数据比前向的 2 次多得多，官方的反向模板常用 8 个 Warp。

### 为什么 D 不用读整行 {#d}

softmax 的梯度需要 $D_i$，它的原始定义是行内点积 $\sum_l P_{il} \, dP_{il}$，要对长度 $N$ 的整行求和，$P_i$ 和 $dP_i$ 可能根本放不进 SRAM。这里有一个恒等式：

$$
D_i = \sum_l P_{il}\, dP_{il} = \sum_l P_{il} \,(dO_i^\top V_l) = dO_i^\top \sum_l P_{il} V_l = dO_i^\top O_i
$$

换算后只需要对长度 $d$ 的向量做点积，代价和序列长度无关。这个变换在 V1 论文的附录 B.4 就有。在 2400 组参数上做数值验证，两边的最大误差约 $4 \times 10^{-15}$。按 Algorithm 2 写的分块反向没有 NaN，结果和直接反向一致（误差约 $9 \times 10^{-15}$），在其中几组小参数上和有限差分也一致（约 $3 \times 10^{-9}$）。$P = \exp(S - L)$ 同样成立，最大误差约 $6 \times 10^{-16}$。

V2 改动的是工程实现：V1 的 Algorithm 4 在每个 Tile 内现算 $D_i$，要读 $O_i$。V2 的 Algorithm 2 提前算好整个 $D$ 写入 HBM，官方实现用一个独立的预处理 Kernel（`compute_dot_do_o`）来算。

### 显存 {#memory}

标准实现要把 $S$ 和 $P$ 落到 HBM，并且保存 $P$ 给反向用，所以显存是 $O(N^2)$。FlashAttention 不落这些矩阵，额外显存是 $O(N)$，也就是 $L$。下表按定义算出这两项，再列出原稿的粗估。

| 序列长度 | $P$（FP16，单头 / 16 头） | $L$（FP32，单头 / 16 头） | 原稿粗估：标准 | 原稿粗估：V2 |
| --- | --- | --- | --- | --- |
| 4K | 32 MiB / 512 MiB | 16 KiB / 256 KiB | 128 MB | 4 MB |
| 16K | 512 MiB / 8 GiB | 64 KiB / 1 MiB | 2 GB | 16 MB |
| 64K | 8 GiB / 128 GiB | 256 KiB / 4 MiB | 32 GB | 64 MB |

<p class="gpu-note">原稿两列是没有说明配置的粗估，来自本文的原始整理稿，没有测量依据。它们的缩放关系是对的（N² 与 N），标准一列相当于每个元素 8 字节、单头。但 V2 一列相当于每个 token 1 KB，远大于 L 本身，只能当作示意。原稿还把 64K 的 32 GB 标为 OOM，单凭这个数字在 80 GB 的卡上并不成立，这里没有保留。前两列只是这两个张量本身的大小，不是训练时的总显存。实测上，论文图 4~6 中 PyTorch 基线在 16k 序列就已经 OOM，说明实际占用远大于这两个单项。论文给出的 V1 整体显存节省是 10~20 倍。</p>

## 小结 {#summary}

每一步都对应一个具体瓶颈：

| 瓶颈 | 改动 | 实际效果 |
| --- | --- | --- |
| SM 用不满 | 外循环改为 Q，沿序列并行 | Block 数乘上 $T_r$，长序列的占用率上来了 |
| O、Q 反复进出 HBM | 同一个调换的副产品 | 同样块大小下总搬运量约降到 2/3，但 K、V 读取变多 |
| 非矩阵乘贵 16 倍 | 延迟归一化，只存 $L$ | 模型估算省 7~14% 时间，$\exp$ 和 rowmax 还在 |
| Warp 之间合并结果 | 沿 Q 切分 | 不再经共享内存合并部分结果 |
| 上三角白算 | 块级跳过（V1 也有） | 实际提速约 1.7~1.8 倍 |

## 检验一下 {#check}

::: details 思考：为什么不把 $T_r$ 也调大，让 Block 数更多？
$T_r$ 变大意味着 $B_r$ 变小，V2 的 K、V 读取量 $2T_r \cdot Nd$ 跟着线性增加。在实验里把 $T_r$ 从 64 拖到 256，总量从 273 MB 涨到 1078 MB。而且 Block 数只要超过 SM 数就够了，再多也不能同时运行。所以并行度够用后，就没有理由继续缩小 $B_r$ 了。
:::

::: details 思考：延迟归一化后，内循环能不能把 $m$ 也延迟掉？
不能直接延迟。$\exp(S - m)$ 里减去最大值是为了数值稳定，也就是防止指数上溢。如果不减，FP32 的指数很容易溢出。$m$ 每次变大时，旧的 $\tilde{O}$ 和 $l$ 都要按 $e^{m^{\text{old}} - m^{\text{new}}}$ 缩放，所以这一步必须留在循环里。
:::

::: details 思考：$L$ 比 $m$、$l$ 少存一个数，怎么够恢复 $P$？
因为反向只需要恢复 $P$：

$$
P_{ij} = e^{S_{ij} - m_i} / l_i = \exp(S_{ij} - L_i)
$$

$m_i$ 和 $\log l_i$ 总是一起出现，它们的和就够了。它们各自的值只在前向累积时才有用。
:::

::: details 思考：Causal Mask 打开后，V2 还比 V1 省搬运量吗？
省的比例差不多。两者访问的 Tile 集合一样，块数都约减半，所以 K、V 和 Q、O 这些按 Tile 计数的项一起减半。实验中 $T_r = T_c = 64$ 时，V1 是 213 MB，V2 是 141 MB，比值还是约 0.66。
:::

::: details 思考：为什么反向不像前向那样沿 Q 并行？
沿 Q 并行时，$dQ_i$ 是独占的，但 $dK_j$、$dV_j$ 就要跨 Block 累加了，而且是两个张量。沿 K/V 并行时只有 $dQ$ 一个张量要累加，通信更少。这也是 Algorithm 2 的内循环中只有 $dQ$ 要写回 HBM 的原因。
:::
